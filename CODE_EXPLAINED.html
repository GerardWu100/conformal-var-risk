The whole thing in plain English

The project asks one narrow question: how much can I lose tomorrow, and which method predicts that number best? It reads five years of minute-by-minute prices for four stocks from a file on disk, turns them into one daily return number per stock per day, then walks forward through 2023 one day at a time. On each day it refits five competing models on the previous 1,150 days and asks each one for the return level that should only be breached 5 percent (and 1 percent) of the time. It records whether tomorrow's real return fell below that level, and at the end it counts how often each model was wrong and whether that count is statistically believable.

The three ways to run it

1. The pipeline. uv run python scripts/run_pipeline.py --config config.toml — does everything and writes five parquet files. Timed at 1 minute 51 seconds here, despite refitting GARCH models several thousand times.
2. The notebook. uv run python -m nbconvert --to notebook --execute --inplace notebooks/demo.ipynb — the identical flow, but each stage prints its intermediate frame. Same cost.

.gitignore contains outputs/**/*.parquet. A fresh clone has no results in it. If you open the notebook expecting numbers, you have to run the pipeline first. The dataclasses are built with **raw_config["section"], so a typo in a TOML key name fails loudly at load time with a TypeError naming the unexpected argument — not silently at model time.

Why frozen dataclasses instead of a plain dictionary

Two reasons. A dictionary would let any function write config["backtest"]["alphas"] = [0.1] mid-run and nothing would complain; frozen=True makes that raise. And a dictionary gives no help when you misspell a key — config["backtst"] raises only at the moment it is read, possibly well into a run.

The weakness, stated honestly

There is no validation beyond "the keys exist and have the right names". Nothing checks that alphas are between 0 and 1, that calibration_window is positive, or that start_date is before end_date. A nonsense value propagates until some numerical function chokes on it.

2,034,240 rows = 4 symbols × 1,304 days × 390 minutes. Counting timestamps by New York hour gives 156,480 bars in the 09:00 hour (that is 30 minutes, 09:30 to 09:59) and 312,960 in each of the hours 10 through 15 (60 minutes each). 30 + 6×60 = 390 minutes per day.

Trap: the date window is cut in UTC, but the sessions are New York

The bounds are built as pd.Timestamp(start_date, tz="UTC") through pd.Timestamp(end_date, tz="UTC") + 1 day - 1 second. Midnight UTC on 1 January 2019 is 7 p.m. New York on 31 December 2018, so the window technically admits a few hours of the previous New York evening. It does no harm here because the session filter in the next stage throws those bars away, and because this particular file contains no after-hours bars at all. On a file that did contain evening bars, and with regular_session_only = false, the first and last trading days would be lopsided.

04Daily returns — build_daily_log_return_panel()

In plain words

Keep only the bars inside normal trading hours, take the last price of each day for each stock, then measure each day's move as the log change from the previous day's close. Finally add a fifth column that averages the four stocks equally, but only on days where all four traded.

What it does

Input: the validated minute-bar frame, the ordered symbol list, and the regular_session_only flag. Output: a wide DataFrame indexed by calendar date with five columns: AAPL, JPM, TSLA, SPY, portfolio. Role: this is the only table the five models ever see. Everything the backtest does traces back to it.

The formula

$$r_{i,t}=\ln\!\left(\frac{C_{i,t}}{C_{i,t-1}}\right) \qquad\qquad r_{\text{port},t}=\frac{1}{N}\sum_{i=1}^{N} r_{i,t}$$

$C_{i,t}$ is the last regular-session close price of stock $i$ on trading day $t$; $r_{i,t}$ is that stock's daily log return, a plain decimal (0.01 means +1 percent); $N=4$ is the number of stocks; $r_{\text{port},t}$ is the equal-weight portfolio return. Log returns are used because they add up across time, which is what the volatility models assume.

Trap: the portfolio column averages log returns, which is an approximation

A genuine equal-weight portfolio's simple return is $\frac1N\sum_i(e^{r_{i,t}}-1)$, and its log return is $\ln\!\big(\frac1N\sum_i e^{r_{i,t}}\big)$ — not $\frac1N\sum_i r_{i,t}$. The two agree to first order and differ by a term of order the variance of the cross-section, so for daily equity moves the gap is a few basis points. It is small, but it is an approximation, and the same shortcut is not taken in the realized-variance module, where the code deliberately averages intraday returns before squaring.

def _append_portfolio_column(
    panel: pd.DataFrame,
    constituent_symbols: list[str],
) -> pd.DataFrame:
    """Append equal-weight portfolio only where all constituents exist."""
    augmented = panel.copy()
    constituent_returns = augmented.reindex(columns=constituent_symbols)
    complete_rows = constituent_returns.notna().all(axis=1)
    augmented["portfolio"] = constituent_returns.mean(axis=1).where(complete_rows)
    return augmented
Why .where(complete_rows) matters

DataFrame.mean(axis=1) skips missing values by default. Without the mask, a day on which only TSLA traded would report TSLA's return as "the portfolio return". The mask forces the portfolio to be missing unless all four constituents are present, so the portfolio series never silently changes its own composition.

05Realized variance — build_daily_realized_variance_panel()

In plain words

For each stock and each day, add up the squares of all 389 minute-to-minute moves. That sum is a direct measurement of how violent the day was, taken from the intraday data rather than estimated from a model. The portfolio's number is built by first forming a minute-by-minute portfolio return, then squaring — not by averaging the four stocks' numbers.

What it does

Input: the same validated minute bars, the symbol list, the session flag. Output: a wide DataFrame indexed by date with the same five columns as the return panel, in squared decimal return units per day (not annualised, not a percentage). Role: feeds the feature table. It does not reach the models.

The formula

$$RV_{i,t}=\sum_{u=2}^{M}\left[\ln\!\left(\frac{P_{i,t,u}}{P_{i,t,u-1}}\right)\right]^{2} \qquad\qquad RV_{\text{port},t}=\sum_{u=2}^{M}\left(\frac{1}{N}\sum_{k=1}^{N} r_{k,t,u}\right)^{2}$$

$P_{i,t,u}$ is the price of stock $i$ at minute $u$ of day $t$; $M=390$ is the number of minute bars in a session, and the sum starts at $u=2$ because the first minute has no preceding bar inside the day; $r_{k,t,u}$ is stock $k$'s log return over minute $u$; $N=4$; $RV$ has units of squared decimal return per day. Expanding the portfolio square gives $RV_{\text{port},t}=\frac{1}{N^{2}}\sum_{k}\sum_{l}\sum_{u} r_{k,t,u}r_{l,t,u}$, which contains every cross-stock covariance term. Averaging the four $RV_{i,t}$ values would keep only the $k=l$ terms and would also use the wrong weight, $1/N$ instead of $1/N^{2}$.

Why the first minute of each day is missing on purpose

intraday_log_return is computed with groupby(["symbol","date"]).transform(...shift(1)), so the 09:30 bar has no return. That deliberately excludes the overnight gap. Realized variance is meant to measure intraday movement; folding in the overnight jump would mix two different things and inflate the number on earnings days. It is worth knowing, though, that the daily returns in section 04 are close-to-close and therefore do include the overnight gap. The two series measure different windows.

The weakness, stated honestly

The realized-variance panel has 1,304 rows while the return panel has 1,303: realized variance needs only one day of data, returns need two. The pipeline patches this with daily_realized_variance.reindex(daily_returns.index) before building features. If a future caller forgets that reindex, build_feature_table() raises rather than silently misaligning — which is the right failure, but it is a landmine that exists only because the two builders disagree about their first row.

Why the timing is safe

Read the shifts carefully. The row labelled date $t$ carries target_next_day_return $=r_{t+1}$, the return you are trying to predict. Every feature on that row is known by the close of day $t$: rv_t is that same day's intraday variance, finished at 16:00; the others are shifted back a further day. So the newest piece of information used to predict $r_{t+1}$ is measured at the close of day $t$, before $r_{t+1}$ exists. There is no look-ahead here. It is also mildly conservative: $|r_t|$ is known at the close of day $t$, yet the code offers only $|r_{t-1}|$ as abs_return_lag_1.

07The model contract — VaRModel and the registry

In plain words

All five forecasters answer the same four questions, so the backtest loop can treat them identically. The one unusual question is observe(): "here is what actually happened, adjust yourself." Four of the five ignore it; the conformal model is the reason it exists.

class VaRModel(ABC):
    @abstractmethod
    def fit(self, returns: np.ndarray) -> None: ...

    @abstractmethod
    def predict_lower_quantile(self, alpha: float) -> float: ...

    def predict_var(self, alpha: float) -> float:
        """Return the positive loss threshold implied by the lower quantile."""
        lower_quantile = self.predict_lower_quantile(alpha=alpha)
        return max(-lower_quantile, 0.0)

    @abstractmethod
    def predict_es(self, alpha: float) -> float: ...

    @abstractmethod
    def predict_interval(self, alpha: float) -> tuple[float, float]: ...

    def observe(self, realized_return: float, alpha: float | None = None) -> None:
        """Update model state after observing the next-day realized return."""
        del realized_return
        del alpha
The two numbers, and why they are different

$$q_{t,\alpha}\ \text{is the return quantile}\qquad \mathrm{VaR}_{t,\alpha}=\max(-q_{t,\alpha},\,0)$$

$\alpha$ is the target left-tail probability, for example $\alpha=0.05$ meaning "the level that should be breached one day in twenty". $q_{t,\alpha}$ is a return, so it is normally negative (−0.021 means "a 2.1 percent loss"). $\mathrm{VaR}_{t,\alpha}$ is a loss amount, so it is reported as a positive number and floored at zero. A violation is recorded when $r_{t}\lt q_{t,\alpha}$ — always against $q$, never against $\mathrm{VaR}$.

Trap: never score against the floored number

The floor at zero is a reporting convention: "you cannot lose a negative amount". But if the raw quantile is positive (a strongly trending window can produce that at $\alpha=0.05$), the floored VaR is exactly 0, and comparing the realized return to 0 would call every down day a violation. The backtest and the pinball loss both use predicted_lower_quantile, the unfloored number, so the score and the adaptive update cannot disagree. Both are stored in the results file, which is why the columns predicted_var and predicted_lower_quantile are mirror images in the sample rows in section 10.

What it does

Input: the config object. Output: a dictionary from model name to a function that takes $\alpha$ and returns a fresh model. Role: lets the backtest build one independent model per (asset, model, $\alpha$) so no state leaks between them.

Why the factories take $\alpha$

The conformal model carries an internal tail level that drifts as it sees errors. It has to start at the level you asked for, so $\alpha$ must be known at construction, not just at prediction time. The other four ignore the argument. The filtered-historical model also uses $\alpha$ to derive its random seed, so the 5 percent run and the 1 percent run draw different bootstrap samples while both stay reproducible: seed $= 11 + \lfloor 0.05\times100000\rfloor + 17 = 5028$ and $11 + 1000 + 17 = 1028$.

The weakness, stated honestly

The seed depends on $\alpha$ but not on the asset. The factory is called once per (asset, $\alpha$) pair, so AAPL, JPM, TSLA, SPY and the portfolio all draw the same sequence of bootstrap indices at the 5 percent level. Their standardized shock pools differ, so the resulting numbers differ; but the sampling noise across the five series is perfectly synchronised rather than independent. With 10,000 draws the sampling noise is tiny, so this changes nothing material — it is worth knowing before someone treats the five series as five independent trials.

08The four benchmarks

1. HistoricalSimulationVaRModel — just look at the past

What it does

Input: the 1,150-day training array; it keeps the last window = 250. Output: the empirical $\alpha$ quantile of those 250 numbers. Role: the "do nothing clever" baseline that every risk desk actually uses.

The formula

$$q_{t,\alpha}=\widehat{F}^{-1}_{250}(\alpha), \qquad \mathrm{ES}_{t,\alpha}=\max\!\left(-\frac{1}{|T|}\sum_{u\in T} r_u,\ \mathrm{VaR}_{t,\alpha}\right), \quad T=\{u: r_u\le q_{t,\alpha}\}$$

$\widehat{F}^{-1}_{250}$ is the empirical inverse distribution function of the last 250 daily returns, computed by np.quantile with linear interpolation between order statistics. $\mathrm{ES}$ is Expected Shortfall: the average loss given that the loss exceeded VaR. $T$ is the set of training days whose return was at or below the quantile. The outer $\max$ prevents ES from ever printing below VaR, which would be nonsense.

Trap: the 1 percent quantile of 250 numbers is two and a half observations

At $\alpha=0.01$ with 250 points, np.quantile interpolates at position $0.01\times249=2.49$, that is between the third and fourth worst days in the window. The estimate is driven by two or three data points and jumps whenever one of them rolls out of the window. This is a known property of historical simulation, not a coding error, and it is why the 1 percent results in section 11 are much noisier than the 5 percent ones.

2 and 3. GarchVaRModel — a volatility model with a distribution bolted on

In plain words

Fit a model that says "today's volatility depends on yesterday's volatility and yesterday's surprise", forecast tomorrow's volatility from it, then read the tail off a bell curve (or a fatter-tailed cousin) scaled to that volatility.

The formula

$$r_u=\mu+\varepsilon_u,\qquad \varepsilon_u=\sigma_u z_u,\qquad \sigma_u^{2}=\omega+\alpha_1\varepsilon_{u-1}^{2}+\beta_1\sigma_{u-1}^{2}$$ $$q_{t,\alpha}=\mu+\sigma_{t}\,z_{\alpha}$$

$\mu$ is a constant average return; $\varepsilon_u$ is the day's surprise; $\sigma_u$ is the conditional volatility (standard deviation) on day $u$; $z_u$ is a standardized shock with mean 0 and variance 1; $\omega,\alpha_1,\beta_1$ are the three fitted GARCH parameters, with $\alpha_1$ controlling how sharply volatility reacts to a shock and $\beta_1$ how long it stays elevated; $\sigma_t$ is the one-day-ahead volatility forecast; $z_\alpha$ is the $\alpha$ quantile of the shock distribution. Here $p=q=1$, taken from config.toml.

The formula — the two shock distributions

Normal shocks: $z_\alpha=\Phi^{-1}(\alpha)$ and $\;E[Z\mid Z\le z_\alpha]=-\dfrac{\phi(z_\alpha)}{\alpha}$.

Student-t shocks with $\nu$ degrees of freedom, rescaled to unit variance:

$$z_\alpha=t^{-1}_\nu(\alpha)\sqrt{\frac{\nu-2}{\nu}}, \qquad E[Z\mid Z\le z_\alpha]=-\left(\frac{\nu+\big(t^{-1}_\nu(\alpha)\big)^{2}}{(\nu-1)\,\alpha}\right) f_\nu\!\big(t^{-1}_\nu(\alpha)\big)\sqrt{\frac{\nu-2}{\nu}}$$

$\Phi^{-1}$ and $\phi$ are the standard normal inverse distribution function and density; $t^{-1}_\nu$ and $f_\nu$ are the raw Student-t inverse distribution function and density with $\nu$ degrees of freedom, $\nu$ being fitted by the arch package (and defaulting to 8 if the fit did not report it). A raw Student-t has variance $\nu/(\nu-2)$, not 1, so both the quantile and the tail mean are multiplied by $\sqrt{(\nu-2)/\nu}$ to make the shock unit-variance and comparable with $\sigma_t$. This requires $\nu\gt2$, which the fitting package enforces.

Why the returns are multiplied by 100 before fitting

arch_model(clean_returns * 100.0, ..., rescale=False). Daily log returns are around 0.01, so their variance is around 0.0001 and the GARCH intercept $\omega$ lands near $10^{-6}$. Optimisers do badly on parameters that small. Multiplying by 100 puts everything in percentage points where the numbers are order 1. Both _forecast_location_scale methods then divide the mean by 100 and the volatility by 100 (the variance by 10,000, implicitly, via the square root) to return to decimals. Get one of those divisions wrong and every VaR number is off by a factor of 100 — the sample box below is the check that they are right.

Why self._last_result = None comes before the try block

The same model object is reused for all 153 evaluation dates. If a refit on day 40 fails and the previous result were left in place, day 40's forecast would silently be produced from day 39's parameters — using information from a window the model was told to discard, and hiding the failure. Clearing the state first means a failed fit falls back to the plain mean and standard deviation of the current window, which is honest and visible. A test in tests/unit/test_models_and_backtest.py monkeypatches arch_model to throw and asserts exactly this.

Trap: except Exception with only a warning

Both GARCH-based models catch every exception and log at WARNING level. The pipeline configures no logging handler, so on a default run these warnings go to standard error via the root logger's last-resort handler and are easy to miss in a long run's output. If a fit silently failed on many days, the results would quietly become a rolling-standard-deviation model. The saving grace is that the fallback is a sane model rather than a crash or a NaN, and the fallback numbers are close enough to the fitted ones that nothing would look obviously broken — which is exactly what makes it worth stating out loud.

4. FilteredHistoricalSimulationVaRModel — GARCH scale, real-world shock shape

In plain words

Use GARCH to say how big tomorrow is likely to be, but instead of assuming the shock follows a bell curve, draw 10,000 shocks at random from the shocks that actually happened in the training window.

The formula

$$\hat z_u=\frac{100\,r_u-\hat\mu}{\hat\sigma_u}, \qquad \tilde r^{(j)}=\hat\mu_{t+1}+\hat\sigma_{t+1}\,\hat z_{B_j},\ \ j=1,\dots,10000, \qquad q_{t,\alpha}=\widehat{F}^{-1}_{10000}(\alpha)$$

$\hat z_u$ is the standardized shock on training day $u$, obtained by removing the fitted mean $\hat\mu$ and dividing by the fitted conditional volatility $\hat\sigma_u$ (both in percentage points, which is why $r_u$ is multiplied by 100); $B_j$ is a uniformly random index into the pool of standardized shocks, drawn with replacement; $\hat\mu_{t+1}$ and $\hat\sigma_{t+1}$ are the one-day-ahead forecasts in decimal units; $\tilde r^{(j)}$ is one simulated next-day return; $\widehat F^{-1}_{10000}$ is the empirical quantile of the 10,000 simulated returns.

Why this usually beats plain GARCH-normal

Plain GARCH-normal gets the scale of tomorrow right but assumes the shape is a bell curve, which understates how often extreme days happen. Historical simulation gets the shape right but assumes the scale never changes, so it is slow to react after a calm stretch. Filtered historical simulation takes the reacting scale from one and the fat-tailed shape from the other. That is the standard argument, and the numbers in section 11 are consistent with it, though 153 days is far too short to call it proven.

09The adaptive conformal model

In plain words

Predict tomorrow with a simple 20-day average. Look back at the last 500 days and record, for each of them, how far below that day's own 20-day average the return actually landed — recording zero on days it landed above. Sort those shortfalls and pick the one at a specific rank. Subtract it from today's 20-day average, and that is the boundary. Then, every day, nudge the internal rank up or down depending on whether the boundary was breached.

What it does

Input: the trailing return array; it keeps the last window = 500. Output: a lower-tail return quantile, plus a rough Expected Shortfall and a diagnostic interval. Role: the method the project exists to test. It is the only model whose observe() does anything.

Step 1: build the scores — fit()

        # One-sided scores compare each rolling-mean forecast to the realized return.
        rolling_centers = self._compute_rolling_mean(trailing_returns)
        realized_segment = trailing_returns[self.mean_window :]
        self._center = float(np.mean(trailing_returns[-self.mean_window :]))
        raw_shortfalls = rolling_centers - realized_segment
        self._scores = np.maximum(raw_shortfalls, 0.0)
        self._pseudo_returns = self._center - self._scores
        self._last_lower_quantile = 0.0
The formula

$$\hat\mu_u=\frac{1}{m}\sum_{k=u-m}^{u-1} r_k \qquad\qquad s_u=\max\!\big(\hat\mu_u-r_u,\ 0\big)$$

$m$ is mean_window = 20, the number of past days averaged; $\hat\mu_u$ is the prediction made for day $u$ using only days strictly before $u$; $r_u$ is what actually happened on day $u$; $s_u$ is the nonconformity score, meaning "how badly did the prediction miss, and only in the direction I care about". Because the tail of interest is the loss tail, an overshoot on the upside scores zero. With a window of 500 returns and $m=20$, exactly $500-20=480$ scores are produced.

Why the score is one-sided

The usual conformal score is $|\hat\mu_u-r_u|$, which builds a two-sided interval. That wastes half the calibration sample on the upside, where a risk manager has no exposure. Clipping at zero means every score measures a downside miss, so the whole 480-point sample is spent describing the shape of the loss tail. The price is that about half the scores are exactly zero — on this window, 49.6 percent of them — so the score distribution has a large point mass at zero. That is harmless for reading a high rank off the sorted array, but it does distort the Expected Shortfall estimate, which is why the code refuses to publish an ES verdict for this model (section 11).

Step 2: pick the rank — _finite_sample_upper_quantile()

        sample_size = len(scores)
        rank = int(np.ceil((sample_size + 1) * (1.0 - alpha)))
        clipped_rank = int(np.clip(rank, 1, sample_size))
        return float(np.partition(scores, clipped_rank - 1)[clipped_rank - 1])
The formula

$$k=\Big\lceil (n+1)\,(1-a_t) \Big\rceil, \qquad \tilde k=\min\!\big(\max(k,1),\,n\big), \qquad q_{t}= \hat\mu_{T} - s_{(\tilde k)}$$

$n$ is the number of calibration scores (480 here); $a_t$ is the model's internal tail level, which starts at the requested $\alpha$ and then drifts; $k$ is the rank to read off the sorted scores; $s_{(\tilde k)}$ is the $\tilde k$-th smallest score; $\hat\mu_T$ is the 20-day average as of today, the point forecast for tomorrow; $q_t$ is the returned lower quantile. The $(n+1)$ rather than $n$ is the standard split-conformal finite-sample correction — it makes the interval very slightly wider so that the guarantee holds exactly on a finite sample rather than only asymptotically.

Why np.partition and not np.sort

Only one order statistic is needed. np.partition does a partial sort that puts the $\tilde k$-th smallest element in its correct slot in $O(n)$ time, instead of $O(n\log n)$ for a full sort. It runs several thousand times per pipeline run, since each of the 1,530 conformal steps calls predict_lower_quantile() three times over — once directly, and once each inside predict_interval() and predict_es(). It is nowhere near the bottleneck, but it is the right tool and it signals that the author knew only one element was wanted.

Trap: the clip is doing real work at the 1 percent level

With $n=480$ and $a_t$ near 0.01, $k=\lceil 481\times0.99\rceil=477$, comfortably inside the array. But observe() can push $a_t$ down as far as MIN_ALPHA = 0.001, giving $k=\lceil481\times0.999\rceil=481\gt480$. Without the clip that would be an IndexError. With it, the model returns the largest score it has ever seen and cannot become any more conservative. That ceiling is real: the model's answer saturates rather than growing without bound.

Step 3: adapt — observe()

    def observe(self, realized_return: float, alpha: float | None = None) -> None:
        """Update the adaptive tail level with a one-sided target-seeking rule."""
        del alpha
        # Lower alpha after a breach, which selects a higher score rank and a more
        # conservative next boundary; raise it after a quiet day.
        breach_indicator = float(realized_return < self._last_lower_quantile)
        updated_alpha = self.current_alpha + self.learning_rate * (
            self._target_alpha - breach_indicator
        )
        self.current_alpha = float(np.clip(updated_alpha, MIN_ALPHA, MAX_ALPHA))
The formula

$$a_{t+1}=\mathrm{clip}\Big(a_t+\gamma\big(\alpha-\mathbf{1}\{r_t\lt q_t\}\big),\ 0.001,\ 0.999\Big)$$

$a_t$ is the internal tail level on day $t$; $\gamma$ is learning_rate = 0.005; $\alpha$ is the target the user asked for, 0.05 or 0.01; $\mathbf{1}\{r_t\lt q_t\}$ is 1 if the realized return fell below the boundary and 0 otherwise. This is the update rule from Gibbs and Candès' adaptive conformal inference. Read the sign carefully: a breach makes the bracket $\alpha-1$, which is negative, so $a_{t+1}$ falls; a lower $a$ means a higher rank $k$, a larger score, and a lower (more conservative) boundary tomorrow. A quiet day makes the bracket $+\alpha$, so $a$ creeps up and the boundary tightens. At the fixed point the long-run breach frequency equals $\alpha$.

Note the asymmetry in the update: a quiet day moves $a$ by $+0.00025$, a breach moves it by $-0.00475$ — nineteen times further. That is what makes the model react fast to a loss and relax slowly afterwards.

The weakness, stated honestly

Split-conformal prediction's finite-sample coverage guarantee requires the calibration scores and the new score to be exchangeable — loosely, that shuffling their order would not change the joint distribution. Daily equity returns are famously not exchangeable: volatility clusters, so a score from March 2020 and a score from July 2021 are drawn from very different conditions. The code uses the exchangeable-case rank $\lceil(n+1)(1-a)\rceil$ anyway, and the docstring says so in as many words. The honest position is that conformal theory supplies the construction here, and the walk-forward backtest supplies the evidence. The adaptive update in step 3 exists precisely because the static guarantee cannot be relied upon.

A second weakness: the Expected Shortfall is a rough proxy

predict_es() averages the "pseudo returns" $\hat\mu_T-s_u$ that lie below the boundary. But roughly half the scores are zero, so half the pseudo returns sit exactly on $\hat\mu_T$ — a synthetic point mass that never existed in the market. The resulting ES is defensible as a rough tail-severity number, and it is not defensible as a statistic to run a formal test on. The metrics module agrees: it labels the conformal model's ES verdict not_reported rather than passing or failing it.

What it does

Input: the wide return panel, the list of $\alpha$ values, the window length, the factory dictionary. Output: one long DataFrame with 11 columns and one row per (date, asset, model, $\alpha$). Role: produces every number the evaluation module scores.

Where look-ahead is prevented, precisely

This is the line a reviewer will point at. Python's slice iloc[i - w : i] excludes position i. So the training array runs from position $i-1150$ up to and including $i-1$, while realized_return is read from position $i$. The day being predicted is never inside the window used to predict it. Verified on real data: with $i=1150$ for SPY, the training window is 2019-01-02 to 2023-05-30 with 1,150 elements, and the evaluation date is 2023-05-31 — the very next trading day. The observe() call comes after the row is written, so the adaptive state used for a forecast never contains that forecast's own outcome.

Why one model object per $\alpha$, and per asset

models_by_alpha = {alpha: model_factory(alpha) for alpha in alphas} sits inside the asset loop and the model loop. That means a fresh conformal model for AAPL at 5 percent, another for AAPL at 1 percent, another for JPM at 5 percent, and so on — twenty-five combinations in all, each carrying its own drifting $a_t$. Sharing one object would let AAPL's breaches tighten JPM's boundary, which is nonsense.

The weakness, stated honestly: 1,150 days of training leaves seven months of testing

The data covers 1,303 trading days. Spending 1,150 of them on the first fit leaves 153 evaluation days, all inside 2023. At $\alpha=0.05$ that is an expected 7.65 violations; at $\alpha=0.01$ it is 1.53. You cannot distinguish models on a sample that thin, and the summary tables in section 11 report exact binomial intervals specifically so nobody pretends otherwise. Trap: dropna() before positional slicing

asset_series = sorted_returns[asset_name].dropna() removes missing days, and the loop then indexes by position. If a series had a two-week hole, the "previous 1,150 days" would silently span a longer calendar stretch and the "next day" would be the next available day, not literally tomorrow. On this dataset the panel is complete, so it does not bite. On a dataset with halted or newly listed names, it would, and nothing in the code would warn you.

Trap: the loop refits every model on every day

model.fit(training_returns) is inside the innermost loop, so each of the three GARCH-based models is re-estimated $153\times5\times2=1530$ times, roughly 4,590 numerical optimisations per run on 1,150 observations each. That is where essentially all of the 1 minute 51 second runtime goes — about 24 milliseconds per fit. It is also the correct thing to do: refitting is what makes it a genuine walk-forward test rather than a single in-sample fit reused. Runtime scales with the number of assets, models and tail levels, so adding three more $\alpha$ values would take it past four minutes.

11Scoring — compute_summary_metrics()

In plain words

Slice the 7,650 forecast rows into named date periods, group them by series, model and tail level, and for each group answer: how often was the boundary breached, is that count believable, how accurate were the forecasts, and were the losses on breach days as bad as predicted.

What it does

Input: the backtest results frame and the evaluation section of the config. Output: one row per (period, asset, model, $\alpha$) with 24 columns. Role: the final artifact. outputs/runs/summary_metrics.parquet, shape (50, 24) on this run.

Pinball loss — the accuracy number

The formula

$$L_\alpha(r,q)=\big(\alpha-\mathbf{1}\{r\lt q\}\big)\,(r-q)$$

$r$ is the realized return, $q$ the forecast quantile, $\alpha$ the tail level. Check both branches: if $r\ge q$ (no breach) the loss is $\alpha(r-q)\ge0$, so being needlessly conservative costs you; if $r\lt q$ (breach) the loss is $(\alpha-1)(r-q)=(1-\alpha)(q-r)\gt0$, so being breached costs you nineteen times more per unit at $\alpha=0.05$. The loss is always non-negative and is minimised, in expectation, by the true $\alpha$ quantile — which is what makes it a fair way to rank quantile forecasts. Also called the check loss or quantile loss.

Christoffersen's two coverage tests

The formula

Unconditional coverage — "is the breach rate right?"

$$LR_{uc}=-2\Big[x\ln\alpha+(n-x)\ln(1-\alpha)-x\ln\hat\pi-(n-x)\ln(1-\hat\pi)\Big]\ \sim\ \chi^2_1$$

Independence — "do breaches cluster?" — and the two combined:

$$LR_{cc}=LR_{uc}+LR_{ind}\ \sim\ \chi^2_2$$

$n$ is the number of forecast days in the group (153 here); $x$ is the number of breaches; $\hat\pi=x/n$ is the observed breach rate; $\alpha$ is the promised rate. $LR$ stands for likelihood ratio: it compares how well the promised rate explains the data against how well the best-fitting rate does. $\chi^2_1$ and $\chi^2_2$ are chi-squared distributions with one and two degrees of freedom. $LR_{ind}$ compares a model where the breach probability depends on whether yesterday was a breach against one where it does not; a large value means breaches arrive in bursts, which is worse for a risk manager than the same number spread out. A large statistic and a small p-value mean the model is rejected.

Clopper-Pearson interval — the honesty column

The formula

$$p_{\text{lo}}=B^{-1}\!\left(\tfrac{1-c}{2};\,x,\,n-x+1\right), \qquad p_{\text{hi}}=B^{-1}\!\left(1-\tfrac{1-c}{2};\,x+1,\,n-x\right)$$

$B^{-1}(\cdot;a,b)$ is the inverse distribution function of the Beta distribution with shape parameters $a$ and $b$; $c=0.95$ is the confidence level; $x$ breaches out of $n$ days. When $x=0$ the lower bound is set to exactly 0, and when $x=n$ the upper bound to exactly 1, because the Beta form is undefined there. This is the exact binomial interval — it never relies on a normal approximation, which matters a great deal when $x$ is 0 or 1.

That trade-off is the most interesting honest result in the project and it is worth stating plainly: over these 153 days the adaptive conformal model was the most conservative and the least accurate. At $\alpha=0.05$ it demanded 17.4 percent more capital than historical simulation (0.024765 against 0.021088) to cut the breach rate from 5.5 percent to 2.9 percent, and its pinball loss was 6.7 percent worse than the best model's. At $\alpha=0.01$ the capital gap widens to 24.1 percent (0.037397 against 0.030129) for zero breaches against one. Whether that is a good trade depends on the cost of capital, and 153 days is far too short to settle it.

The formula — the two Expected Shortfall tests

$$Z_1=\frac{1}{N_T}\sum_{t\in T}\frac{r_t}{\mathrm{ES}_t}+1 \qquad\qquad Z_2=\frac{1}{n}\sum_{t=1}^{n}\frac{r_t\,\mathbf{1}\{r_t\lt q_t\}}{\alpha\,\mathrm{ES}_t}+1$$

These are the Acerbi-Székely statistics. $T$ is the set of breach days and $N_T$ its size; $r_t$ is the realized return on a breach day, which is negative; $\mathrm{ES}_t$ is the predicted Expected Shortfall, a positive loss amount. If predictions are right, the ratio $r_t/\mathrm{ES}_t$ averages $-1$ and each statistic averages 0. A clearly negative statistic means realized losses were worse than predicted, so ES was understated. $Z_1$ conditions on breaches only and says nothing about whether the breach count was right; $Z_2$ divides by $n$ and by $\alpha$ instead, so it punishes both too many breaches and too-severe breaches. The code turns each into a one-sided p-value with a $\sqrt{N}\bar x/s$ statistic read against a normal distribution, and labels the outcome from $Z_2$.

Why the conformal ES verdict is refused rather than reported

classify_es_backtest() returns "not_reported" for the conformal model before it looks at any number. The reason is the point mass at zero described in section 09: the pseudo-return sample the conformal ES is averaged over is partly synthetic, so a pass or a fail would not mean what a reader would take it to mean. Declining to score is more honest than scoring something that does not deserve it. The same function returns "insufficient_tail_data" when there were too few breaches to compute anything, rather than printing a NaN and letting a reader guess.

Trap: the confidence level for the violation-rate interval is fixed in code

_summarize_period() calls clopper_pearson_interval(..., confidence_level=0.95) as a literal, while the ES label threshold comes from config.toml as es_backtest_confidence. The literal is deliberate to the extent that the output column names encode it (violation_rate_ci_95_lower, violation_rate_ci_95_upper) — making it configurable would require the column names to change with it. Worth knowing before someone edits the config expecting the interval to move.

Why the project root is derived from the config file's location

Every relative path in config.toml — data/raw, outputs/runs — is resolved against the folder holding the config file, not against the shell's current directory. So uv run python scripts/run_pipeline.py works identically from the repository root, from scripts/, or from anywhere else. This is also what lets the end-to-end test point at a config file inside a temporary folder and have the whole pipeline read and write inside that folder.

What it returns

A frozen PipelineArtifacts dataclass holding the five output paths, which the command-line script prints as key=path lines. That makes the script's output easy to consume from a shell script without parsing prose.

18If someone points at a line

The questionThe answer
"Where exactly do you prevent look-ahead?"Three places. backtest.py: the training slice ends at position $i-1$ and the realized return is read at position $i$. backtest.py: observe() is called after the row is written, so adaptive state never contains its own outcome. feature_builder.py: the target is shift(-1) and every feature is either same-day-close or shifted back further.
"Why is VaR positive but the quantile negative?"The quantile is a return, the VaR is a loss amount: $\mathrm{VaR}=\max(-q,0)$. Both are stored. All scoring uses the quantile, never the floored loss, so a rare positive quantile cannot make every down day look like a breach.
"Your conformal model breaches least often. Is it the best?"No, and the numbers say so. At $\alpha=0.05$ it has the highest pinball loss (0.001409 against 0.001321 for filtered historical) and the largest average VaR (0.024765 against 0.021088 for historical simulation). It is buying a lower breach rate with more capital, not with better forecasts.
"Do you claim the conformal coverage guarantee?"No. The guarantee needs exchangeable scores; daily equity returns cluster in volatility and are not exchangeable. The docstring in conformal.py says this. Conformal theory supplies the construction; the walk-forward backtest supplies the evidence.
"Why is realized variance built at all?"Honestly: it feeds a feature table that no model currently reads. It is correctly built and correctly timed, and it is unconsumed. The obvious next step for the project is a model that actually uses it.
"Why average intraday returns before squaring for the portfolio?"Because $\mathrm{Var}(\frac1N\sum r_i)=\frac1{N^2}\sum_k\sum_l \mathrm{Cov}(r_k,r_l)$ contains cross terms. Averaging the four variances drops every covariance and uses $1/N$ where $1/N^2$ belongs. On 16 March 2020 the difference is 6.75e-06 against 2.43e-05, a factor of 3.6.
"Why multiply returns by 100 before the GARCH fit?"Numerical conditioning. The variance intercept would otherwise be around $10^{-6}$ and the optimiser struggles. Both forecast methods divide back by 100 afterwards; the sample box in section 08 confirms the round trip.
"What if a GARCH fit fails?"The previous result is cleared first, so the fallback is the current window's mean and standard deviation, never yesterday's fitted parameters. There is a test that monkeypatches arch_model to throw and asserts this.
"How long does it take, and why?"1 minute 51 seconds, measured. Three of the five models refit a GARCH model on every one of $153\times5\times2$ steps, which is about 4,590 numerical optimisations at roughly 24 milliseconds each. Refitting is the point of a walk-forward test, so this is a cost rather than a waste.
"Why do three of your four evaluation periods print nothing?"The 1,150-day training window consumes everything before 31 May 2023, so all 153 evaluation days sit in 2023. The covid, rate-shock and post-covid windows all end before that. Lowering calibration_window is what would bring them back.
"Can I trust a 3.3 percent breach rate against a 5 percent target?"Not on its own. The exact 95 percent interval for 5 breaches in 153 days runs from 1.07 percent to 7.46 percent, which contains 5 percent comfortably. The interval column exists precisely so this question has a number attached to it.

19Honest limitations

Stated before anyone asks
  1. 153 evaluation days is not enough to rank five models. Every 95 percent interval in the summary table contains the target rate. The project reports those intervals rather than declaring a winner, which is the right call, but it means no model is shown to be better than another here.
  2. The realized-variance work does not reach any forecast. Two of the six modules exist to build a feature table nothing reads.
  3. The conformal coverage guarantee does not apply. Financial returns are not exchangeable. The code uses the exchangeable-case rank and says so; the adaptive update exists because the static guarantee cannot be leaned on.
  4. The conformal Expected Shortfall is partly synthetic because roughly half the one-sided scores are zero. The code refuses to publish an ES verdict for it, which is honest, but it also means the model is only half-evaluated.
  5. The tracked dataset appears to be synthetic or reconstructed. It contains a bar for 1 January 2019, which was a market holiday, and exactly 390 bars for every symbol on every one of 1,304 days — real minute data has gaps, halts and short days. The pipeline is real; treat the specific numbers as a demonstration of the machinery, not as a claim about the 2023 equity market.
  6. The portfolio return averages log returns rather than compounding properly. The error is second order and small at daily frequency, but it is an approximation, and notably the realized-variance module does not take the same shortcut.
  7. Bootstrap randomness is synchronised across the five series because the filtered-historical seed depends on the tail level but not on the asset. Immaterial at 10,000 draws; relevant if anyone treats the five series as independent trials.
  8. No logging is configured. A GARCH fit that fails on many days would degrade the model to a rolling standard deviation, and the only trace would be warnings on standard error amid the pipeline's normal output.
