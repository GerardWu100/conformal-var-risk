Reading the conformal Value-at-Risk pipeline

A short guide to the folders, data flow, and key decisions, using numbers from an actual run of this repository.

How to use this

Sections follow the order in which the code runs. Every snippet comes from src/conformal_var_risk/. Every number in a grey Sample data box came from running this repository on its tracked input (data/raw/minute_bars.parquet, 2,034,240 rows) on 10 August 2026. Coloured boxes mark design choices, traps, and weaknesses. This page explains the structure and behaviour, not every line.

The whole thing in plain English

The project asks one narrow question: how much can I lose tomorrow, and which method predicts that number best? It reads five years of minute-by-minute prices for four stocks, turns them into one daily return per stock, and moves through 2023 one day at a time. Each day it refits five competing models on the previous 1,150 days. Each model returns a loss threshold that should be breached only 5 percent (and 1 percent) of the time. The pipeline records whether the next day's return fell below that threshold, then counts each model's breaches and tests whether the count is statistically believable.

The three ways to run it

1. The pipeline. uv run python scripts/run_pipeline.py --config config.toml runs everything and writes five parquet files. It took 1 minute 51 seconds here, including several thousand refits of Generalized Autoregressive Conditional Heteroskedasticity (GARCH) models.
2. The notebook. uv run python -m nbconvert --to notebook --execute --inplace notebooks/demo.ipynb — the same flow, but each stage prints its intermediate table. It takes about as long.
3. The tests. uv run python -m pytest runs 24 tests in about 3 seconds, including one end-to-end run on a small synthetic dataset built inside the test file.

Trap: the parquet outputs are not tracked

.gitignore contains outputs/**/*.parquet, so a fresh clone has no results. Run the pipeline before opening the notebook if you expect numbers. The frozen comma-separated value (CSV) files under blog/data/ are the only committed results; they let the blog charts be redrawn without running the pipeline again.

The dataclasses are built with **raw_config["section"]. A misspelled Tom's Obvious Minimal Language (TOML) key therefore raises a TypeError at load time and names the unexpected argument, instead of failing later inside a model.

Why frozen dataclasses instead of a plain dictionary

Two reasons. A dictionary would let any function write config["backtest"]["alphas"] = [0.1] during a run; frozen=True makes that raise immediately. A dictionary also gives no help with misspelled keys: config["backtst"] fails only when that key is read, possibly well into a run.

The weakness, stated honestly

Validation stops at "the keys exist and have the right names". Nothing checks that alphas are between 0 and 1, that calibration_window is positive, or that start_date is before end_date. A nonsense value propagates until some numerical function rejects it.

2,034,240 rows = 4 symbols × 1,304 days × 390 minutes. Counting timestamps by New York hour gives 156,480 bars in the 09:00 hour (that is 30 minutes, 09:30 to 09:59) and 312,960 in each of the hours 10 through 15 (60 minutes each). So 30 + 6×60 = 390 minutes per day.

Trap: the date window is cut in Coordinated Universal Time (UTC), but the sessions are New York

The bounds use pd.Timestamp(start_date, tz="UTC") through pd.Timestamp(end_date, tz="UTC") + 1 day - 1 second. Midnight UTC on 1 January 2019 is 7 p.m. New York on 31 December 2018, so the window technically admits a few hours of the previous New York evening. That causes no problem here: the next stage removes those bars, and this file has no after-hours bars. On a file that did contain evening bars, with regular_session_only = false, the first and last trading days would be uneven.

04Daily returns — build_daily_log_return_panel()

In plain words

Keep normal trading hours, take each stock's last price of the day, and measure the change from the previous day's close. Then add an equal-weight average for the four stocks, but only on days when all four traded.

What it does

Input: the validated minute-bar table, the ordered symbol list, and the regular_session_only flag. Output: a wide DataFrame indexed by calendar date with five columns: AAPL, JPM, TSLA, SPY, portfolio. Role: this is the only table the five models see. The backtest traces back to it.

The formula

$$r_{i,t}=\ln\!\left(\frac{C_{i,t}}{C_{i,t-1}}\right) \qquad\qquad r_{\text{port},t}=\frac{1}{N}\sum_{i=1}^{N} r_{i,t}$$

$C_{i,t}$ is the last regular-session close price of stock $i$ on trading day $t$; $r_{i,t}$ is that stock's daily log return, a plain decimal (0.01 means +1 percent); $N=4$ is the number of stocks; $r_{\text{port},t}$ is the equal-weight portfolio return. Log returns are used because they add across time, as the volatility models assume.

Trap: the portfolio column averages log returns, which is an approximation

A genuine equal-weight portfolio's simple return is $\frac1N\sum_i(e^{r_{i,t}}-1)$, and its log return is $\ln\!\big(\frac1N\sum_i e^{r_{i,t}}\big)$ — not $\frac1N\sum_i r_{i,t}$. The two agree to first order and differ by a term related to the cross-sectional variance, so for daily equity moves the gap is a few basis points (hundredths of a percentage point). It is small, but it is an approximation, and the same shortcut is not taken in the realized-variance module, where the code averages intraday returns before squaring.

def _append_portfolio_column(
    panel: pd.DataFrame,
    constituent_symbols: list[str],
) -> pd.DataFrame:
    """Append equal-weight portfolio only where all constituents exist."""
    augmented = panel.copy()
    constituent_returns = augmented.reindex(columns=constituent_symbols)
    complete_rows = constituent_returns.notna().all(axis=1)
    augmented["portfolio"] = constituent_returns.mean(axis=1).where(complete_rows)
    return augmented
Why .where(complete_rows) matters

DataFrame.mean(axis=1) skips missing values by default. Without the mask, a day when only TSLA traded would report TSLA's return as the portfolio return. The mask leaves the portfolio missing unless all four stocks are present, so its composition cannot change silently.

05Realized variance — build_daily_realized_variance_panel()

Plain English

For each stock and day, add the squares of all 389 minute-to-minute moves. The sum measures that day's intraday movement directly. For the portfolio, first form a minute-by-minute portfolio return, then square it; do not average the four stocks' values.

What it does

Input: the same validated minute bars, the symbol list, and the session flag. Output: a wide DataFrame indexed by date with the same five columns as the return panel, in squared decimal return units per day (not annualised, not a percentage). Role: feeds the feature table; the models do not use it.

The formula

$$RV_{i,t}=\sum_{u=2}^{M}\left[\ln\!\left(\frac{P_{i,t,u}}{P_{i,t,u-1}}\right)\right]^{2} \qquad\qquad RV_{\text{port},t}=\sum_{u=2}^{M}\left(\frac{1}{N}\sum_{k=1}^{N} r_{k,t,u}\right)^{2}$$

$P_{i,t,u}$ is the price of stock $i$ at minute $u$ of day $t$; $M=390$ is the number of minute bars in a session, and the sum starts at $u=2$ because the first minute has no preceding bar inside the day; $r_{k,t,u}$ is stock $k$'s log return over minute $u$; $N=4$; $RV$ has units of squared decimal return per day. Expanding the portfolio square gives $RV_{\text{port},t}=\frac{1}{N^{2}}\sum_{k}\sum_{l}\sum_{u} r_{k,t,u}r_{l,t,u}$, which contains every cross-stock covariance term, which captures how stocks move together. Averaging the four $RV_{i,t}$ values would keep only the $k=l$ terms and would also use the wrong weight, $1/N$ instead of $1/N^{2}$.

Why the first minute of each day is missing on purpose

intraday_log_return uses groupby(["symbol","date"]).transform(...shift(1)), so the 09:30 bar has no return. That deliberately excludes the overnight gap. Realized variance is meant to measure intraday movement; folding in the overnight jump would mix two different things and inflate the number on earnings days. It is worth knowing, though, that the daily returns in section 04 are close-to-close and therefore do include the overnight gap. The two series measure different windows.

The weakness, stated honestly

The realized-variance panel has 1,304 rows while the return panel has 1,303: realized variance needs one day of data, while returns need two. The pipeline fixes the mismatch with daily_realized_variance.reindex(daily_returns.index) before building features. If a future caller forgets that reindex, build_feature_table() raises rather than silently misaligning — which is the right failure, but it is a landmine that exists only because the two builders disagree about their first row.

Why the timing is safe

Read the shifts carefully. The row labelled date $t$ carries target_next_day_return $=r_{t+1}$, the return you are trying to predict. Every feature on that row is known by the close of day $t$: rv_t is that same day's intraday variance, finished at 16:00; the others are shifted back a further day. So the newest piece of information used to predict $r_{t+1}$ is measured at the close of day $t$, before $r_{t+1}$ exists. There is no look-ahead bias here: the model does not use future information. It is also mildly conservative: $|r_t|$ is known at the close of day $t$, yet the code offers only $|r_{t-1}|$ as abs_return_lag_1.

07The model contract — VaRModel and the registry

Plain English

All five forecasters use the same interface, so the backtest can treat them alike. The unusual method is observe(): it tells a model what happened so it can adjust. Four models ignore it; the conformal model needs it.

class VaRModel(ABC):
    @abstractmethod
    def fit(self, returns: np.ndarray) -> None: ...

    @abstractmethod
    def predict_lower_quantile(self, alpha: float) -> float: ...

    def predict_var(self, alpha: float) -> float:
        """Return the positive loss threshold implied by the lower quantile."""
        lower_quantile = self.predict_lower_quantile(alpha=alpha)
        return max(-lower_quantile, 0.0)

    @abstractmethod
    def predict_es(self, alpha: float) -> float: ...

    @abstractmethod
    def predict_interval(self, alpha: float) -> tuple[float, float]: ...

    def observe(self, realized_return: float, alpha: float | None = None) -> None:
        """Update model state after observing the next-day realized return."""
        del realized_return
        del alpha
The two numbers, and why they are different

$$q_{t,\alpha}\ \text{is the return quantile}\qquad \mathrm{VaR}_{t,\alpha}=\max(-q_{t,\alpha},\,0)$$

$\alpha$ is the target probability in the left tail, for example $\alpha=0.05$ meaning "the level that should be breached one day in twenty". $q_{t,\alpha}$ is a return, so it is normally negative (−0.021 means "a 2.1 percent loss"). $\mathrm{VaR}_{t,\alpha}$ is a loss amount, so it is reported as a positive number and floored at zero. A violation is recorded when $r_{t}\lt q_{t,\alpha}$ — always against $q$, never against $\mathrm{VaR}$.

Trap: never score against the floored number

The floor at zero is only a reporting convention: "you cannot lose a negative amount". If the raw quantile is positive (a strongly trending window can produce that at $\alpha=0.05$), the floored VaR is exactly 0, and comparing the realized return to 0 would call every down day a violation. The backtest and the pinball loss both use predicted_lower_quantile, the unfloored number, so the score and the adaptive update cannot disagree. Both are stored in the results file, which is why the columns predicted_var and predicted_lower_quantile are mirror images in the sample rows in section 10.

What it does

Input: the config object. Output: a dictionary from model name to a function that takes $\alpha$ and returns a fresh model. Role: lets the backtest build one independent model per (asset, model, $\alpha$), so state cannot leak between them.

Why the factories take $\alpha$

The conformal model carries an internal tail level that changes as it sees errors. It must start at the level you asked for, so $\alpha$ must be known at construction, not just at prediction time. The other four ignore the argument. The filtered-historical model also uses $\alpha$ to derive its random seed, so the 5 percent run and the 1 percent run draw different bootstrap samples while both stay reproducible: seed $= 11 + \lfloor 0.05\times100000\rfloor + 17 = 5028$ and $11 + 1000 + 17 = 1028$.

The weakness, stated honestly

The seed depends on $\alpha$ but not on the asset. The factory is called once per (asset, $\alpha$) pair, so AAPL, JPM, TSLA, SPY and the portfolio all draw the same sequence of bootstrap indices at the 5 percent level. Their standardized shock pools differ, so the resulting numbers differ; but the sampling noise across the five series is perfectly synchronised rather than independent. With 10,000 draws the sampling noise is tiny, so this changes nothing material — it is worth knowing before someone treats the five series as five independent trials.

08The four benchmarks

1. HistoricalSimulationVaRModel — just look at the past

What it does

Input: the 1,150-day training array; it keeps the last window = 250. Output: the empirical $\alpha$ quantile of those 250 numbers. Role: the simple baseline: use the recent past without adding a model.

The formula

$$q_{t,\alpha}=\widehat{F}^{-1}_{250}(\alpha), \qquad \mathrm{ES}_{t,\alpha}=\max\!\left(-\frac{1}{|T|}\sum_{u\in T} r_u,\ \mathrm{VaR}_{t,\alpha}\right), \quad T=\{u: r_u\le q_{t,\alpha}\}$$

$\widehat{F}^{-1}_{250}$ is the empirical inverse distribution function of the last 250 daily returns, computed by np.quantile with linear interpolation between ordered observations. $\mathrm{ES}$ is Expected Shortfall: the average loss given that the loss exceeded VaR. $T$ is the set of training days whose return was at or below the quantile. The outer $\max$ keeps ES from falling below VaR.

Trap: the 1 percent quantile of 250 numbers is two and a half observations

At $\alpha=0.01$ with 250 points, np.quantile interpolates at position $0.01\times249=2.49$, between the third and fourth worst days in the window. Two or three observations drive the estimate, and it jumps when one leaves the window. This is a property of historical simulation, not a coding error, and it explains why the 1 percent results in section 11 are much noisier than the 5 percent results.

2 and 3. GarchVaRModel — a volatility model with a distribution bolted on

Plain English

Fit a model in which today's volatility depends on yesterday's volatility and surprise. Forecast tomorrow's volatility, then read the tail from a normal distribution or a heavier-tailed Student-t distribution scaled to it.

The formula

$$r_u=\mu+\varepsilon_u,\qquad \varepsilon_u=\sigma_u z_u,\qquad \sigma_u^{2}=\omega+\alpha_1\varepsilon_{u-1}^{2}+\beta_1\sigma_{u-1}^{2}$$ $$q_{t,\alpha}=\mu+\sigma_{t}\,z_{\alpha}$$

$\mu$ is a constant average return; $\varepsilon_u$ is the day's surprise; $\sigma_u$ is the conditional volatility (the standard deviation) on day $u$; $z_u$ is a standardized shock with mean 0 and variance 1; $\omega,\alpha_1,\beta_1$ are the three fitted GARCH parameters, with $\alpha_1$ controlling how sharply volatility reacts to a shock and $\beta_1$ how long it stays elevated; $\sigma_t$ is the one-day-ahead volatility forecast; $z_\alpha$ is the $\alpha$ quantile of the shock distribution. Here $p=q=1$, taken from config.toml.

The formula — the two shock distributions

Normal shocks: $z_\alpha=\Phi^{-1}(\alpha)$ and $\;E[Z\mid Z\le z_\alpha]=-\dfrac{\phi(z_\alpha)}{\alpha}$.

Student-t shocks with $\nu$ degrees of freedom, rescaled to unit variance:

$$z_\alpha=t^{-1}_\nu(\alpha)\sqrt{\frac{\nu-2}{\nu}}, \qquad E[Z\mid Z\le z_\alpha]=-\left(\frac{\nu+\big(t^{-1}_\nu(\alpha)\big)^{2}}{(\nu-1)\,\alpha}\right) f_\nu\!\big(t^{-1}_\nu(\alpha)\big)\sqrt{\frac{\nu-2}{\nu}}$$

$\Phi^{-1}$ and $\phi$ are the standard normal inverse distribution function and density; $t^{-1}_\nu$ and $f_\nu$ are the raw Student-t inverse distribution function and density with $\nu$ degrees of freedom, $\nu$ being fitted by the arch package (and defaulting to 8 if the fit did not report it). A raw Student-t has variance $\nu/(\nu-2)$, not 1, so both the quantile and the tail mean are multiplied by $\sqrt{(\nu-2)/\nu}$ to make the shock unit-variance and comparable with $\sigma_t$. This requires $\nu\gt2$, which the fitting package enforces.

Why the returns are multiplied by 100 before fitting

arch_model(clean_returns * 100.0, ..., rescale=False). Daily log returns are around 0.01, so their variance is around 0.0001 and the GARCH intercept $\omega$ lands near $10^{-6}$. Optimisers do badly on parameters that small. Multiplying by 100 puts everything in percentage points where the numbers are order 1. Both _forecast_location_scale methods then divide the mean by 100 and the volatility by 100 (the variance by 10,000, implicitly, via the square root) to return to decimals. Get one of those divisions wrong and every VaR number is off by a factor of 100 — the sample box below is the check that they are right.

4. FilteredHistoricalSimulationVaRModel — GARCH scale, real-world shock shape

Plain English

Use GARCH to estimate tomorrow's scale, but draw 10,000 shocks from the training window instead of assuming they follow a bell curve.

The formula

$$\hat z_u=\frac{100\,r_u-\hat\mu}{\hat\sigma_u}, \qquad \tilde r^{(j)}=\hat\mu_{t+1}+\hat\sigma_{t+1}\,\hat z_{B_j},\ \ j=1,\dots,10000, \qquad q_{t,\alpha}=\widehat{F}^{-1}_{10000}(\alpha)$$

$\hat z_u$ is the standardized shock on training day $u$, obtained by removing the fitted mean $\hat\mu$ and dividing by the fitted conditional volatility $\hat\sigma_u$ (both in percentage points, which is why $r_u$ is multiplied by 100); $B_j$ is a uniformly random index into the pool of standardized shocks, drawn with replacement; $\hat\mu_{t+1}$ and $\hat\sigma_{t+1}$ are the one-day-ahead forecasts in decimal units; $\tilde r^{(j)}$ is one simulated next-day return; $\widehat F^{-1}_{10000}$ is the empirical quantile of the 10,000 simulated returns.

Why this usually beats plain GARCH-normal

GARCH-normal models tomorrow's scale but assumes the shape is a bell curve, which understates extreme days. Historical simulation keeps the observed shape but assumes the scale never changes, so it reacts slowly after a calm stretch. Filtered historical simulation combines GARCH's changing scale with the observed shock shape. The numbers in section 11 are consistent with that explanation, but 153 days is far too short to prove it.

09The adaptive conformal model

Plain English

Predict tomorrow with a simple 20-day average. For the last 500 days, measure how far each return fell below its own 20-day average, using zero when it stayed above. Choose a shortfall at a specified rank, subtract it from today's 20-day average, and use the result as the boundary. Each day, adjust the internal rank according to whether the boundary was breached.

What it does

Input: the trailing return array; it keeps the last window = 500. Output: a lower-tail return quantile, a rough Expected Shortfall, and a diagnostic interval. Role: the method the project exists to test. It is the only model whose observe() does anything.

Step 1: build the scores — fit()

        # One-sided scores compare each rolling-mean forecast to the realized return.
        rolling_centers = self._compute_rolling_mean(trailing_returns)
        realized_segment = trailing_returns[self.mean_window :]
        self._center = float(np.mean(trailing_returns[-self.mean_window :]))
        raw_shortfalls = rolling_centers - realized_segment
        self._scores = np.maximum(raw_shortfalls, 0.0)
        self._pseudo_returns = self._center - self._scores
        self._last_lower_quantile = 0.0
The formula

$$\hat\mu_u=\frac{1}{m}\sum_{k=u-m}^{u-1} r_k \qquad\qquad s_u=\max\!\big(\hat\mu_u-r_u,\ 0\big)$$

$m$ is mean_window = 20, the number of past days averaged; $\hat\mu_u$ is the prediction made for day $u$ using only days strictly before $u$; $r_u$ is what actually happened on day $u$; $s_u$ is the nonconformity score: how badly the prediction missed, but only in the direction that matters here. Because the tail of interest is the loss tail, an overshoot on the upside scores zero. With a window of 500 returns and $m=20$, exactly $500-20=480$ scores are produced.

Why the score is one-sided

The usual conformal score is $|\hat\mu_u-r_u|$, which builds a two-sided interval. That spends half the calibration sample on the upside, where a risk manager has no exposure. Clipping at zero makes every score measure a downside miss, so all 480 points describe the loss tail. The cost is that about half the scores are exactly zero — 49.6 percent on this window. This is fine when reading a high rank from the array, but it distorts the Expected Shortfall estimate. That is why the code does not publish an ES verdict for this model (section 11).

Step 2: pick the rank — _finite_sample_upper_quantile()

        sample_size = len(scores)
        rank = int(np.ceil((sample_size + 1) * (1.0 - alpha)))
        clipped_rank = int(np.clip(rank, 1, sample_size))
        return float(np.partition(scores, clipped_rank - 1)[clipped_rank - 1])
The formula

$$k=\Big\lceil (n+1)\,(1-a_t) \Big\rceil, \qquad \tilde k=\min\!\big(\max(k,1),\,n\big), \qquad q_{t}= \hat\mu_{T} - s_{(\tilde k)}$$

$n$ is the number of calibration scores (480 here); $a_t$ is the model's internal tail level, which starts at the requested $\alpha$ and then changes; $k$ is the rank to read from the sorted scores; $s_{(\tilde k)}$ is the $\tilde k$-th smallest score; $\hat\mu_T$ is the 20-day average as of today, the point forecast for tomorrow; $q_t$ is the returned lower quantile. The $(n+1)$ rather than $n$ is the standard split-conformal finite-sample correction — it makes the interval very slightly wider so that the guarantee holds exactly on a finite sample rather than only asymptotically.

Why np.partition and not np.sort

Only one ordered value is needed. np.partition places the $\tilde k$-th smallest element in its correct slot in $O(n)$ time, instead of $O(n\log n)$ for a full sort. It runs several thousand times per pipeline run, since each of the 1,530 conformal steps calls predict_lower_quantile() three times over — once directly, and once each inside predict_interval() and predict_es(). It is nowhere near the bottleneck, but it is the right tool and it signals that the author knew only one element was wanted.

Trap: the clip is doing real work at the 1 percent level

With $n=480$ and $a_t$ near 0.01, $k=\lceil 481\times0.99\rceil=477$, inside the array. But observe() can push $a_t$ down as far as MIN_ALPHA = 0.001, giving $k=\lceil481\times0.999\rceil=481\gt480$. Without the clip that would be an IndexError. With it, the model returns the largest score it has ever seen and cannot become any more conservative. That ceiling is real: the model's answer saturates rather than growing without bound.

Step 3: adapt — observe()

    def observe(self, realized_return: float, alpha: float | None = None) -> None:
        """Update the adaptive tail level with a one-sided target-seeking rule."""
        del alpha
        # Lower alpha after a breach, which selects a higher score rank and a more
        # conservative next boundary; raise it after a quiet day.
        breach_indicator = float(realized_return < self._last_lower_quantile)
        updated_alpha = self.current_alpha + self.learning_rate * (
            self._target_alpha - breach_indicator
        )
        self.current_alpha = float(np.clip(updated_alpha, MIN_ALPHA, MAX_ALPHA))
The formula

$$a_{t+1}=\mathrm{clip}\Big(a_t+\gamma\big(\alpha-\mathbf{1}\{r_t\lt q_t\}\big),\ 0.001,\ 0.999\Big)$$

$a_t$ is the internal tail level on day $t$; $\gamma$ is learning_rate = 0.005; $\alpha$ is the target the user asked for, 0.05 or 0.01; $\mathbf{1}\{r_t\lt q_t\}$ is 1 if the realized return fell below the boundary and 0 otherwise. This is the update rule from Gibbs and Candès' adaptive conformal inference. Read the sign carefully: a breach makes the bracket $\alpha-1$, which is negative, so $a_{t+1}$ falls; a lower $a$ means a higher rank $k$, a larger score, and a lower (more conservative) boundary tomorrow. A quiet day makes the bracket $+\alpha$, so $a$ creeps up and the boundary tightens. At the fixed point the long-run breach frequency equals $\alpha$.

The weakness, stated honestly

Split-conformal prediction's finite-sample coverage guarantee requires the calibration scores and the new score to be exchangeable: roughly, their joint distribution should not change when their order is shuffled. Daily equity returns are not exchangeable because volatility clusters. A score from March 2020 and one from July 2021 come from different conditions. The code still uses the exchangeable-case rank $\lceil(n+1)(1-a)\rceil$. Conformal theory supplies the construction; the walk-forward backtest supplies the evidence. The adaptive update in step 3 exists because the static guarantee cannot be trusted here.

A second weakness: the Expected Shortfall is a rough proxy

predict_es() averages the "pseudo returns" $\hat\mu_T-s_u$ below the boundary. Roughly half the scores are zero, so half the pseudo returns sit exactly on $\hat\mu_T$: a synthetic value that never occurred in the market. The resulting ES is reasonable as a rough measure of tail severity, but not as the input to a formal test. The metrics module therefore labels the conformal model's ES verdict not_reported.

Plain English

What it does

Input: the backtest results frame and the evaluation section of the config. Output: one row per (period, asset, model, $\alpha$) with 24 columns. Role: the final artifact. outputs/runs/summary_metrics.parquet, shape (50, 24) on this run.

Pinball loss — the accuracy number

The formula

$$L_\alpha(r,q)=\big(\alpha-\mathbf{1}\{r\lt q\}\big)\,(r-q)$$

$r$ is the realized return, $q$ the forecast quantile, and $\alpha$ the tail level. Check both branches: if $r\ge q$ (no breach) the loss is $\alpha(r-q)\ge0$, so being needlessly conservative costs you; if $r\lt q$ (breach) the loss is $(\alpha-1)(r-q)=(1-\alpha)(q-r)\gt0$, so being breached costs you nineteen times more per unit at $\alpha=0.05$. The loss is always non-negative and is minimised, in expectation, by the true $\alpha$ quantile — which is what makes it a fair way to rank quantile forecasts. Also called the check loss or quantile loss.

Christoffersen's two coverage tests

The formula

Unconditional coverage — "is the breach rate right?"

$$LR_{uc}=-2\Big[x\ln\alpha+(n-x)\ln(1-\alpha)-x\ln\hat\pi-(n-x)\ln(1-\hat\pi)\Big]\ \sim\ \chi^2_1$$

Independence — "do breaches cluster?" — and the two combined:

$$LR_{cc}=LR_{uc}+LR_{ind}\ \sim\ \chi^2_2$$

$n$ is the number of forecast days in the group (153 here); $x$ is the number of breaches; $\hat\pi=x/n$ is the observed breach rate; $\alpha$ is the promised rate. $LR$ means likelihood ratio: it compares how well the promised rate explains the data with the best-fitting rate. $\chi^2_1$ and $\chi^2_2$ are chi-squared distributions with one and two degrees of freedom. $LR_{ind}$ compares a model where the breach probability depends on whether yesterday was a breach against one where it does not; a large value means breaches arrive in bursts, which is worse for a risk manager than the same number spread out. A large statistic and a small p-value mean the model is rejected.

Clopper-Pearson interval — the honesty column

The formula

$$p_{\text{lo}}=B^{-1}\!\left(\tfrac{1-c}{2};\,x,\,n-x+1\right), \qquad p_{\text{hi}}=B^{-1}\!\left(1-\tfrac{1-c}{2};\,x+1,\,n-x\right)$$

$B^{-1}(\cdot;a,b)$ is the inverse distribution function of the Beta distribution with shape parameters $a$ and $b$; $c=0.95$ is the confidence level; $x$ breaches out of $n$ days. When $x=0$ the lower bound is set to exactly 0, and when $x=n$ the upper bound to exactly 1, because the Beta form is undefined there. This is the exact binomial interval — it never relies on a normal approximation, which matters a great deal when $x$ is 0 or 1.

The formula — the two Expected Shortfall tests

$$Z_1=\frac{1}{N_T}\sum_{t\in T}\frac{r_t}{\mathrm{ES}_t}+1 \qquad\qquad Z_2=\frac{1}{n}\sum_{t=1}^{n}\frac{r_t\,\mathbf{1}\{r_t\lt q_t\}}{\alpha\,\mathrm{ES}_t}+1$$

These are the Acerbi-Székely statistics. $T$ is the set of breach days and $N_T$ its size; $r_t$ is the realized return on a breach day, which is negative; $\mathrm{ES}_t$ is the predicted Expected Shortfall, a positive loss amount. If predictions are right, the ratio $r_t/\mathrm{ES}_t$ averages $-1$ and each statistic averages 0. A clearly negative statistic means realized losses were worse than predicted, so ES was understated. $Z_1$ conditions on breaches only and says nothing about whether the breach count was right; $Z_2$ divides by $n$ and by $\alpha$ instead, so it punishes both too many breaches and too-severe breaches. The code turns each into a one-sided p-value with a $\sqrt{N}\bar x/s$ statistic read against a normal distribution, and labels the outcome from $Z_2$.

Why the conformal ES verdict is refused rather than reported

classify_es_backtest() returns "not_reported" for the conformal model before looking at any number. As section 09 explains, its pseudo-return sample is partly synthetic, so a pass or fail would be misleading. The same function returns "insufficient_tail_data" when there were too few breaches to compute anything, rather than printing a NaN and letting a reader guess.

Trap: the confidence level for the violation-rate interval is fixed in code

_summarize_period() calls clopper_pearson_interval(..., confidence_level=0.95) with a literal, while the ES label threshold comes from config.toml as es_backtest_confidence. The literal is deliberate to the extent that the output column names encode it (violation_rate_ci_95_lower, violation_rate_ci_95_upper) — making it configurable would require the column names to change with it. Changing the config therefore does not move this interval.

Plain English

Every relative path in config.toml — data/raw, outputs/runs — is resolved against the folder holding the config file, not against the shell's current directory. 18If someone points at a line

QuestionAnswer
"Where exactly do you prevent look-ahead?"Three places. backtest.py: the training slice ends at position $i-1$ and the realized return is read at position $i$. backtest.py: observe() runs after the row is written, so adaptive state never contains its own outcome. feature_builder.py: the target is shift(-1), and every feature is same-day-close information or older.
"Why is VaR positive but the quantile negative?"The quantile is a return, the VaR is a loss amount: $\mathrm{VaR}=\max(-q,0)$. Both are stored. All scoring uses the quantile, never the floored loss, so a rare positive quantile cannot make every down day look like a breach.
"Your conformal model breaches least often. Is it the best?"No. At $\alpha=0.05$ it has the highest pinball loss (0.001409 against 0.001321 for filtered historical) and the largest average VaR (0.024765 against 0.021088 for historical simulation). It buys a lower breach rate with more capital, not better forecasts.
"Do you claim the conformal coverage guarantee?"No. The guarantee needs exchangeable scores; daily equity returns cluster in volatility and are not exchangeable. The docstring in conformal.py says this. Conformal theory supplies the construction; the walk-forward backtest supplies the evidence.
"Why is realized variance built at all?"It feeds a feature table that no model currently reads. It is correctly built and timed, but unused. The next step is a model that actually uses it.
"Why average intraday returns before squaring for the portfolio?"Because $\mathrm{Var}(\frac1N\sum r_i)=\frac1{N^2}\sum_k\sum_l \mathrm{Cov}(r_k,r_l)$ contains cross terms. Averaging the four variances drops every covariance and uses $1/N$ where $1/N^2$ belongs. On 16 March 2020 the difference is 6.75e-06 against 2.43e-05, a factor of 3.6.
"Why multiply returns by 100 before the GARCH fit?"Numerical conditioning. The variance intercept would otherwise be around $10^{-6}$ and the optimiser struggles. Both forecast methods divide back by 100 afterwards; the sample box in section 08 confirms the round trip.
"What if a GARCH fit fails?"The previous result is cleared first, so the fallback is the current window's mean and standard deviation, never yesterday's fitted parameters. There is a test that monkeypatches arch_model to throw and asserts this.
"How long does it take, and why?"1 minute 51 seconds, measured. Three of the five models refit GARCH on every one of $153\times5\times2$ steps: about 4,590 numerical optimisations at roughly 24 milliseconds each. Refitting is required for a walk-forward test, so this is an unavoidable cost.
"Why do three of your four evaluation periods print nothing?"The 1,150-day training window consumes everything before 31 May 2023, so all 153 evaluation days sit in 2023. The covid, rate-shock and post-covid windows all end before that. Lowering calibration_window is what would bring them back.
"Can I trust a 3.3 percent breach rate against a 5 percent target?"Not by itself. The exact 95 percent interval for 5 breaches in 153 days runs from 1.07 percent to 7.46 percent, which contains 5 percent. The interval gives the uncertainty a number.

19Honest limitations

Limitations
  1. 153 evaluation days is not enough to rank five models. Every 95 percent interval in the summary table contains the target rate. The project reports those intervals instead of declaring a winner, so no model is shown to be better than another here.
  2. The realized-variance work does not reach any forecast. Two of the six modules build a feature table that nothing reads.
  3. The conformal coverage guarantee does not apply. Financial returns are not exchangeable. The code uses the exchangeable-case rank and says so; the adaptive update exists because the static guarantee cannot be relied on.
  4. The conformal Expected Shortfall is partly synthetic because roughly half the one-sided scores are zero. The code refuses to publish an ES verdict for it, which is honest, but it also means the model is only half-evaluated.
  5. The tracked dataset appears synthetic or reconstructed. It contains a bar for 1 January 2019, which was a market holiday, and exactly 390 bars for every symbol on every one of 1,304 days — real minute data has gaps, halts and short days. The pipeline is real; treat the specific numbers as a demonstration of the machinery, not as a claim about the 2023 equity market.
  6. The portfolio return averages log returns rather than compounding properly. The error is second order and small at daily frequency, but it is an approximation, and notably the realized-variance module does not take the same shortcut.
  7. Bootstrap randomness is synchronised across the five series because the filtered-historical seed depends on the tail level but not on the asset. Immaterial at 10,000 draws; relevant if anyone treats the five series as independent trials.
  8. No logging is configured. Many failed GARCH fits would reduce the model to a rolling standard deviation; the only trace would be warnings on standard error among the normal pipeline output.
